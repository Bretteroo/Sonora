# Translation

Sonora's own strings -- what the shared components and the shared browse parts
render, in every theme -- live in one file per locale under
`app/frontend/src/i18n/`, keyed identically and named for the locale's BCP 47
language tag:

    en-US.js   reference catalog, 888 keys
    cs-CZ.js   Czech
    da-DK.js   Danish
    de-DE.js   German
    es-ES.js   Spanish
    fr-FR.js   French
    hu-HU.js   Hungarian
    it-IT.js   Italian
    fi-FI.js   Finnish
    ja-JP.js   Japanese
    ko-KR.js   Korean
    nb-NO.js   Norwegian (Bokmål)
    nl-NL.js   Dutch
    pl-PL.js   Polish
    pt-BR.js   Portuguese (Brazil)
    pt-PT.js   Portuguese (Portugal)
    sv-SE.js   Swedish
    uk-UA.js   Ukrainian
    zh-CN.js   Chinese (Simplified)
    zh-TW.js   Chinese (Traditional)

A locale, not a language. `en-US` and `en-GB` would be different catalogs, so
would `pt-BR` and `pt-PT`, and `zh-CN` and `zh-TW` are not spelling variants of
one another -- Simplified and Traditional Chinese differ in vocabulary as well
as in characters, and neither is a fallback for the other. The tag is what the
interface stores, what the backend is told, and what a music service is asked
for, so a locale has one spelling everywhere rather than three.

`app/frontend/src/i18n/locales.js` is the registry: the tag, the name the locale
calls itself by (which is what the chooser shows), its English name, and its
fallback chain. `app/backend/locale.py` is the same list for the backend, and
`app/tests/test_locale.py` fails if the two disagree.

## Themes

A theme's own strings are the theme's own file. `app/themes/<id>/strings.js` --
at the repository's own `app/themes/`, beside the frontend rather than inside it
-- carries every locale in one file, and the theme names it in its manifest:

    import strings from './strings.js'
    export default { id: 'outrun', ..., strings, tokens, Shell }

They are laid over the core catalog while that theme is the chosen one, so a
theme carries everything it says as well as everything it draws, and a theme
folder can be deleted without leaving words behind. Two themes may use the
same key for different words; only the chosen theme's are ever merged. A theme
that renders another theme's string keeps its own copy of it -- Liquid Glass
wears Sonofuture's shell and carries its own copy of what that shell says --
because reaching into another theme's folder is what the copy is there to
avoid.

A string that shared code renders, or that more than one theme renders, is
Sonora's and stays in the core catalog. `app/tests/test_theme_strings.py` fails
when a string only one theme says is left there, and when a theme names a key
it cannot reach.

## Fallback

`en-US` is the reference and the only catalog guaranteed complete. A key
missing from another catalog is looked for along that locale's chain and then
in the reference, so a partial translation degrades into mixed language
instead of into debug output. In development a missing key also logs a
warning.

The chain is where a locale's near relatives go: `pt-BR` reads `pt-PT` before
English, once there is a `pt-PT` to read. Chinese has no chain in either
direction.

Placeholders are written `{name}` and substituted at render time, so word order
can differ between locales. `t('web.group.title', { room: 'Pantry' })`.

## Counts

Keys whose wording changes with a count carry explicit `.one` and `.other`
variants, reached through `t.plural('common.rooms', n)`. This is spelled out
rather than delegated to a pluralisation library because the set is small and
the catalogs disagree about it: Spanish pluralises the noun after a numeral,
Hungarian does not, and Japanese, Korean, and both Chinese catalogs have no
plural at all. `common.rooms.one` and `common.rooms.other` are therefore
identical in several files, which is correct rather than a copy-paste slip.

## Selection and negotiation

The locale is chosen in the settings dialog and persisted to `localStorage`.
On first run it is detected from `navigator.languages`: an exact tag wins, a
language match takes the registry's locale for that language, and Chinese is
never guessed across scripts -- a bare `zh` falls back to English rather than
picking a side. Choosing a locale also sets `document.documentElement.lang`,
which browsers use for hyphenation and screen readers use to pick a voice.

The page sends the chosen tag as `Accept-Language` on every request it makes.
Sonora's middleware negotiates that header against `SUPPORTED` -- honoring
q-values -- and keeps the result in a context variable for the life of the
request, so the backend does not thread a language argument through forty call
sites. What reads it:

- **SMAPI.** A music service takes the language from the `Accept-Language`
  header of the SOAP call, so browse headings and messages come back in the
  reader's locale rather than always in English.
- **Presentation maps.** A service's map carries one strings table per
  language; the cache is keyed by locale so two readers do not share one.
- **Extended metadata.** `getExtendedMetadata` returns the message a rating
  button shows, in the language it was asked for.

A service with no table for a locale answers in its own default, which is its
business rather than something to guess around.

## Adding a locale

Add the tag to `LOCALES` in `app/frontend/src/i18n/locales.js` and to `SUPPORTED`
in `app/backend/locale.py`, then build the catalog from the reference: copy
`en-US.js` to `<tag>.js` and translate each value in place, and do the same
for each theme's `strings.js`. Keep the reference's comments, key order and
wrapping, so a new catalog reads like a translation of `en-US.js` rather than
like machine output. Then import it in
`app/frontend/src/i18n/index.jsx` and add it to the `CATALOGS` map.

`app/tests/test_i18n_parity.py` discovers catalogs by globbing the directory, so a
new file is checked as soon as it exists -- it fails when a locale loses a key
or spells a placeholder differently, in the core catalog and in every theme's
`strings.js` alike. To check one by hand while translating:

    node --input-type=module -e "
    import en from './src/i18n/en-US.js';
    import other from './src/i18n/xx-XX.js';
    const keys = Object.keys(en);
    console.log('missing:', keys.filter(k => !(k in other)));
    console.log('extra:', Object.keys(other).filter(k => !(k in en)));
    console.log('placeholder mismatch:', keys.filter(k => k in other &&
      (en[k].match(/\{\w+\}/g)||[]).sort().join() !==
      (other[k].match(/\{\w+\}/g)||[]).sort().join()));
    "

## Keeping the translations honest

`app/tests/test_i18n_parity.py` fails when a catalog loses a key or spells a
placeholder differently. It cannot see the commoner problem: an English value
is reworded, the others keep their old wording, every key still lines up, and
the translations are wrong with nothing to show for it. Nothing about that is
visible at runtime -- the reader simply gets a sentence that no longer says
what the English says.

So each translated value carries a fingerprint of the English it was made
from, in `translated-from.json` beside the catalogs. Before every release the
maintainer compares those fingerprints with the English as it stands, using a
checker kept outside the repository, translates every key whose English has
moved since, in the core catalog and in each theme's own file, and only then
records the current English as translated.

Editing an English string by hand is fine and expected -- the release check is what
makes it safe, rather than a rule against it.

## What is not translated yet

Diagnostic findings are composed as English prose in the backend
(`app/backend/sonos/network.py`), with measurements interpolated into the
sentences. Translating them means having the backend return a finding code
plus its data and letting the frontend compose the sentence, which is the
right shape anyway. Until that refactor the troubleshooting page shows
translated column headings and English findings.
